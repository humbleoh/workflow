# Topic-Note-Loop — 写审反哺闭环

把一篇大纲条目笔记生成并迭代到**干净**（无内容违规），并把审阅暴露的**规则缺口**反哺回规则文件与写作技能。本技能只做**编排、分流、收敛、反哺**——不代写笔记内容、不代判规则：写作交给 `topic-note-writer`，审阅交给 `topic-note-reviewer`，判定依据只有 `riz-topic-note-rules/rules.md`。

闭环四步对应：**生成内容 → 审阅内容 → 反哺技能 → 重复**。收敛对象是单篇笔记；反哺在收敛后统一进行、逐条确认后落回。

## 1. 分工

| 用户要的 | 用 |
| --- | --- |
| 为大纲某条目写一篇笔记 | topic-note-writer |
| 审阅一篇笔记、出问题清单与反哺建议 | topic-note-reviewer |
| 把一篇笔记迭代到干净 + 反哺规则 | **本技能** |

## 2. 前置

1. 规则文件路径确认：`riz-topic-note-rules/rules.md`（与三技能同处 `反刍/SKILLS/`）。
2. 目标条目确认：`0. 大纲.md` 里哪个条目（`*(TODO)*` 或已链接）。
3. 挖惯例由 `topic-note-writer` 阶段一完成，本技能不代做；但须先确认条目名**机制本体单一**（规则文件 §2）——若条目名并列两个独立概念，先提请用户拆条目再进循环。

## 3. 闭环流程

### 循环体（对单篇笔记）

1. **生成 / 修订**：经 `subagent` 派遣 writer 角色（fresh context），产出初稿或按上轮问题清单修订笔记。
2. **审阅**：经 `subagent` 派遣 reviewer 角色（fresh context），产出问题清单（内容违规 + 规则缺口）。
3. **分流**：
   - **内容违规** → 回到 1，由 writer 按上轮问题清单修订（fresh context，把问题清单整体交给 writer）；仅琐碎项（缩写全称、标点、链接补全）可由编排者直接改后回到 2。
   - **规则缺口** → 记入反哺清单（不在本轮改规则），回到 2。
4. **判终**：问题清单无「内容违规」→ 收敛，进入反哺；否则回到 1（见收敛守卫）。

### 收敛守卫

- 内容违规修复至多 **3 轮**；3 轮后仍不收敛 → 停止循环，把残余问题清单与当前笔记交用户决断。
- 同一条「高」级违规连续 **2 轮**未消失 → 判定修复无效，停止并说明，交人工。
- 规则缺口不计入终止条件（它是「现行规则没管到」，不是「违反现行规则」）；本轮笔记是否回头补修该缺口，作为反哺清单里的可选项交用户。

### 反哺（收敛后）

1. 把反哺清单逐条列给用户：每条给「缺口现象 + 建议落在 rules.md 哪个 § + writer 哪个阶段」。
2. 用户确认后落回，三处同步：rules.md 对应 § + rules.md §7 合规清单补一条检查 + writer 对应阶段补一条动作（落点映射见 §5）。
3. 落回后（可选）用更新后的规则对笔记复检一次，确认无因规则更新而新出现的违规。

## 4. 子代理协议

- 两角色都 fresh context，每次迭代**新开**子代理，不传上一轮记忆——独立性是审阅有效的前提，上下文污染会带回偏见。
- writer 子代理提示词：载入 `topic-note-writer` 技能，读 `riz-topic-note-rules/rules.md`，附「目标条目 + 大纲上下文 +（若为修订）上一轮问题清单」。
- reviewer 子代理提示词：载入 `topic-note-reviewer` 技能，读 `riz-topic-note-rules/rules.md`，附「笔记全文」；**不附**写作过程中的任何辩解或上下文。
- 本技能（主代理）不代写、不代审，只在两子代理之间搬运产物与清单。

## 5. 反哺落点映射

| 缺口类型 | rules.md | writer 阶段 |
| --- | --- | --- |
| 依据（溯源、分级、内嵌、电子书、穷举） | §1 | 阶段二 收依据 |
| 结构（骨架、机制本体单一、边界、前置） | §2 | 阶段一 挖惯例 / 阶段三 写正文 |
| 深度（因果 / 设计取舍 / 历史成因） | §3 | 阶段三 写正文 |
| 干货（量化事实、反直觉结论、反判据） | §4 | 阶段三 写正文 |
| 行文（朴实、叙述体、概称、术语、总起对账） | §5 | 阶段三 写正文 |
| 图片（图文一致、命名、渲染核对） | §6 | 阶段三 写正文 |

> 落回时三处同步：rules.md 对应 § 增判据 → §7 合规清单增检查项 → writer 对应阶段增动作。只改一处会让规则沦为「没人查的条款」。

## 6. 交付汇报

汇报四项：笔记路径、收敛轮数、反哺了几条规则缺口、改了 rules.md / writer 哪几处（含 §7 与阶段的同步）。

## 7. 常见错误

| 错误 | 纠正 |
| --- | --- |
| 主代理自己代写 / 代审 | 编排者不生产、不判定；写审都派遣 fresh-context 子代理 |
| 把规则缺口当内容违规拿来阻塞收敛 | 规则缺口不计入终止条件；它进反哺清单，收敛后统一处理 |
| 反哺不确认就改 rules.md / writer | 逐条确认后落回（用户已定「确认后改」） |
| 只改 rules.md，不同步 §7 清单与 writer 阶段 | 三处同步，否则规则没人查 |
| 无限循环（修不干净就硬跑） | 3 轮守卫；同一「高」级违规连 2 轮未消即停 |
| 把内容违规与规则缺口判错 | 判定交给 reviewer，本技能不重新判定，只按清单分流 |
| 每次迭代复用同一子代理会话 | 每轮新开 fresh context，独立性优先 |
