# Topic-Note Rules — 主题笔记写作规则（共享契约）

本文件是「大纲条目笔记」的**契约**：一篇合格笔记必须满足的全部规则，按「依据 → 结构 → 深度 → 干货 → 行文 → 图片 → 合规清单」组织。

- **写作技能** `topic-note-writer` 据此产出：其四阶段流程（挖惯例 → 收依据 → 写正文 → 接线）中的「收依据」「写正文」两阶段直接引用本文件。
- **审阅技能** `topic-note-reviewer` 据此检查：逐条对照本文件，产出问题清单并区分「内容违规」与「规则缺口」。

本文件只陈述**判据**（什么算合格、什么算违规），不陈述流程（怎么挖惯例、怎么接线——见写作技能）。

**核心原则**：笔记是其大纲条目的忠实展开——初学者可读、角色定重心、技术断言逐一可溯源（依据内嵌正文）、例子先于机制、因果与取舍讲透、干货落地、文风朴实高密度、形式从库惯例、与姊妹条目划清边界、前置概念不卡读者。初学者要的不是结论清单，而是结论怎么来的；「因果、设计取舍、历史成因讲透 + 干货落地」是硬要求，也是笔记与「手册拷贝」的分界。

## 1. 依据契约（证据分级与内嵌）

### 1.1 权威分级（级别随链接文字或附录标注；正文引用以链接内嵌呈现）

| 级 | 来源 | 用法 |
| --- | --- | --- |
| 1 | 官方文档：语言标准、参考手册（RM）、应用笔记（AN）、RFC | 定义与语义的首要依据；正文中文转述＋出处链接缀尾（在线文档优先取带章节锚点的 HTML 版）；逐字引文不上正文，进 references 底账 |
| 1 | 本地实验（实际运行代码 / 上板实测） | 行为类断言的首要依据；正文标「实测」 |
| 2 | 官方实现源码/头文件/例程、官方 KB、官方员工在官方论坛的答复、PEP、经典教材 | 设计动机、实现细节、官方对行为的定性；员工原话可 `> [!quote]`。**源码逐行实核**时对行为类断言是一手证据、强度等价 1 级——以链接内嵌到文件（含行号）呈现；仅给章节锚点未逐字核的，链接只到章节 |
| 2 | 社区实测线程（他人上板/运行的实录） | 无本地实验条件时的行为依据；标「实测」+ 链接 |
| 3 | 权威二级来源（cppreference 类、Stack Overflow 高票实测） | 辅助，标注「编辑性概述」，引用附链接 |
| 4 | 博客 | 仅取直觉与图解，不作断言依据 |

> 百科类来源（Wikipedia 等）不在上表分级内：只能作为寻找一手/官方来源的索引，不得作为「定义与语义」的首要依据；确以百科为准时须标注「编辑性概述」，相关断言降级为「转引/待考」，或回追其引用的一级来源（应用笔记/规范/手册）核对。

### 1.2 内嵌规则

- **依据强度体现在链接精确度**：**逐行实核** → 链接内嵌到文件（含行号）；**章节级锚点** → 链接只到章节、未逐字核；**未核** → 无链接、内联「待考」；**推断** → 内联「（推断）」并给理由。正文不用「实核 / 转引」这类孤立加粗标记——链接本身就是出处标注
- **必须实际查阅，禁止凭记忆落笔**：用 webfetch / context7 / librarian 查官方文档；「会怎样」类行为优先本地实验，无条件实验时引 2 级实测来源
- **依据内嵌正文，一步点达**：凡有据断言，先说人话（中文陈述），在线来源缀链接、不用圆括弧包裹（库内来源 `[[笔记]]` 同样缀尾）——断言是主角，出处是缀尾旁注。**在线文档优先取带章节锚点的 HTML 版**（RFC 用 `https://www.rfc-editor.org/rfc/NNNN.html#section-N.M`，锚点即定位，免翻文内目录）。**链接文本按位置分型**：句尾（句号/问号/分号前、表格单元格末）纯隐形 `[](url#anchor)`；句中（顿号/破折号/逗号前，行文继续处）标记入链 `[§N.M](url#anchor)`；名字作句子成分时写进链接（`即 [RFC 1057](url)，取代…`）。不产出「`[](URL)` 后缀裸 `§x` 文本」旧式。空链接 `[](url)` 紧贴前文、不留空格——空链接渲染为零宽，前置空格即成标点前的悬空空格（渲染成「字面量 ；」）；表格单元格 `| [](url) |` 的对齐留白不受此限。锚点以页面 `id="…"` 实核为准，HTML 版无对应小节/分段锚（如 RFC 4506 §5 的分段编号 (2)）时锚到最近父级节、正文标记保留原引用号（`[§5(3)](…#section-5)`）。不写「（同上）」，同一来源的多处断言各自挂链接。**逐字引文原则上不上正文**（先甩原句后解释会打断初学者）：正文转述＋缀尾链接即可溯源，逐字原文留 references 底账；确需正文逐字时，先给一句中文引入再引，引入标记用「原文：」、不用「逐字：」。确无链接的来源（纸质书等离线资料）在附录注明获取方式
- **本地电子书可链接定位，不算「离线」**：vault 内已有电子书 PDF 的经典教材，先经 pdf 工具（检索/读页）定位并核对原文，再引 `[[books/书名.pdf#page=N|…]]`——页码进锚点，**不写进正文文字**；正文旁注出处用下标小图标 `<sub style="font-size:0.6em">[[books/…#page=N|↗]]</sub>`，不加圆括弧；表格依据格用 `[[…|⧉]]`（下标样式在表格内不用）；逐字引用处用 `> [!quote]` + 描述性别名作标题（如 `[[…|书名/§1.1]]`），callout 类型已表明逐字，标题不写「逐字引自」。书页码与 PDF 页码常相差前置页数，不一致时正文提书页码、锚点给 PDF 页码；页锚锚住承载该断言**原文**的那一页——断言所述表格/图在另一页时，以正文文字所在页为准，必要时两页各挂其位；书中断言若在正文或 references 写出章节号，章节号必须与页锚同一次核验得出（先查目录再落笔），不写未经目录核验的章节号。**书中有对应原文的断言，不再引幻灯片/二手转述**；仅某版本独有的内容保留该版本出处并注明
- **转引复用**：库内既有笔记已核过的依据可经 `[[笔记]]` 内嵌转引（`[[X]]` 本身即链接、天然标注「经 X 转引」）——**不占查阅预算**；但转引不得超出原笔记核过的断言范围。前置/姊妹笔记已核的**反例**可转引为本篇动机段的因果起点（如「3.4 反例一」引出本篇盲区），不占预算
- **增量/无新增断言自述须自查**：落「只做 N 件增量」「本篇无新增独立断言」类全称自述前，须 grep 姊妹篇逐条核对每条「增量」确未被他篇覆盖、逐句核对正文无超出转引范围的断言；确有新断言则另立依据并显式列出，不得一并塞进「转引」
- **不可得诚实标记**：来源不可达（WAF 拦截等）时，用 `> [!info]` 说明获取状态，相关断言降级为内联「转引」/「待考」——诚实标记，不是省略
- **穷举断言须 grep 穷举**：「全库一致」「仅此 N 处」「仅此一条路径」类全称/存在性断言，必须 grep 全库检索并逐点列行号，不得凭印象写「应该就这几处」；行号内嵌进正文链接（`[sector_write.c L412](URL)`），注释逐字处用 `> [!quote]` 摘录
- **非标准文本在线文档的示例级断言须版本固定**：RFC、语言标准之外的在线官方文档（指南页、博客页）无版本化 URL、可整页重写——断言若依赖页内**具体示例或字节数**，须①本地实测兜底并在正文就近标「实测」，②给 archive 版本锚或注明检索日期（如「核对于 2026-09」）；正文只引页面稳定承载的部分（公式、规则、对照表）
- **「为何」类断言另立取证**：设计动机引官方设计理由（源码注释、应用笔记、官方 KB、官方员工答复），历史成因引旧版文档、标准修订史、勘误（errata）、迁移指南；与「是什么」类断言同等严格，**不得凭常识替设计师编动机**
- **转述保真、不放大范围**：概括不得超出原文承载面——原文由「某装置的 X 组件 / 某协议」承载的断言，不写成整个装置；规范、参考实现、产品三层写清（如「DCE 的 RPC 组件线路协议成为微软 RPC 基底」，不是「DCE 成为微软 DCOM 的基底」）
- **自建框架显式归属**：笔记自行构造的分层/分型/谱系（所引来源无此划分）以直陈句给出时，首句内联标明为本篇整理（如「代理结构本篇整理为三层」），不得以「通用结构分 N 层」类来源腔陈述自建分类——读者须能分辨哪些是书的结构、哪些是笔记的框架；分类轴附一句白话（按什么维度分，如「解释知识放在哪」），表头与类名不得是无所指的抽象词（「知识来源」类）
- 版本/型号敏感的语法与行为，行内标注（如 (3.10+)、H753 vs H743）

## 2. 结构契约（笔记骨架，按序）

**机制本体单一**：一篇笔记只承载一个可问答的机制本体。标题以「与 / 及」并列两个概念的，须证明二者是同一机制的两种表述（如因果两端），否则拆成两篇——初学者分不清两个未展开概念的界限。

**标题不与姊妹篇同名**：机制本体委派给姊妹篇、本篇为应用/惯用法时，标题以动作或场景命名（如「为从器件选对 SPI 模式」），不得复用机制名词，尤其不得与姊妹机制篇标题同名或为其子串。

1. `# 中文名 English Name`——与大纲条目同名（文件名亦然）
2. 开篇段：`**术语**：一句话定义 + 一句话在本主题中的位置`。定义不可循环——不用被定义词或其同位语自证，从内存/机制层给非循环解释；「X 是 Y」先核 X 的本体归属（如 GType 是数值 ID，注册表属于类型系统）。**与姊妹条目有重叠面时，此处即给边界声明**——「X 的机制本体在 [[Y]]；本篇是第 N 章惯用法，回答 Z」；视角差异一句话点明（如「那是静态状态视角，本篇是动态转移视角」）。**主题问句前置**：开篇即点明本篇回答的核心问题（「本篇的主题是 X，回答一个问题：Y」）；「不展开、归姊妹篇」类路由压缩成短句缀尾，不挤占主题位置
3. `> [!info] 前置阅读`——有前置概念时写，紧随开篇段：已写笔记列 `[[链接]]`，未写的标 `名（TODO 待落地）`。未写前置在正文首现处给一句最小定义（够读懂本篇即可，不展开）
4. `## 动机 / 问题背景`——机制出现前的问题（**因果起点**）；有真实历史成因时在此交代「何时 / 为何引入、留下什么兼容包袱」；应用/惯用法篇先摆出两个世界（如开发 vs 生产）的矛盾要求；必要时用 `> [!info]` 说明笔记定位或依据获取状态
5. `## 定义与机制`——主体。认知顺序：最小例子 → 机制讲解（**因果链显式成链 + 设计取舍**）→ 边界与反例 → `### 速查`；母题对接例证（如「GStreamer 侧对接：」）放机制与边界之后殿后，不混进机制段打断叙述
   - **最小例子按域取形**：软件域给 ≤ 30 行可运行代码；嵌入式/硬件域给最小配置序列、官方源码片段（注明出处）、伪代码判定流程或分支树；例子引出后一句点明它正是开篇定义的最小兑现（定义里的术语各对应例中哪个物事），后文机制讲解优先回用例中的对象与代码行作锚，不让例子与主题脱钩；示例所用的调用首次出现前先立最小场景（它替谁解决什么问题），并声明为**全篇参照物**——机制段、自绘图、速查表统一沿用同一示例名，不出现正文 `append` 而图里 `add` 的分叉；场景开头直接从事情本身写起（如「单机上的程序要把一条记录追加进数据库时，只需写下一行 …」），不用「先立一个最小场景：」类口号式元叙述；**示例是正文机制的兑现**——示例代码所体现的规则与数字须与正文机制断言一致，正文规则修订后回查示例代码、其输出、及该数字在全文（对比句、速查表、references）的全部引用，与 §6「正文修订后回查图」同责；正文以「正是／对应 X 接口／X 的最小实现」背书示例时，X 的每个成员逐项在示例中有对应物，确有未收的成员就地显式声明（如「第四项 notify 本例未收」）
   - **源码删减摘录的忠实边界**：删减用 `...` 显式标注；**守卫条件、判据分支、状态位序列不得删**——删的是样板（如重复的分配调用）而非语义分支；关键逻辑被删处，用注释补足被删步骤的语义，不得让控制流读起来变味
   - **表格只在真需对照时用，因果叙事为主**：机制讲解以「因果链成段」为主体，不把每个断言拆成「断言 | 依据」格（那是碎片化清单，不是讲解）。确需对照表（分支树、两模式对照）时，依据格用**内嵌链接**（`[file.c L412](URL)`、`[[笔记]]`），禁止无链接的裸来源名；依据格须覆盖行内**每条**断言——行内含多条断言而依据格只挂其一时，为其余断言补各自依据（跨篇依据同样以 `[[链接]]` 入格）；引本篇自身论证时用实测编号或标题锚链接，不用「上文／前述」类无链接裸指
   - 误解、工程陷阱、归因陷阱（工具假象先归因再下结论）、待考边界清单，用 `> [!warning]`
   - 末尾 `### 速查` 表收束：「维度 → 值」或「问题 → 答案」；**速查表答案只做正文已论证结论的改写**，不得引入正文未论证的新判据或新括注——新判据先在正文成段论证（证据＋买单方）后方可进表
6. `## 与相关概念的关系`——关系类型：**上位 / 上游 / 同层 / 对照 / 下游 / 跨学科**；已写笔记用 `[[链接]]`，未写的标 TODO（带章节号）
7. `## 相关笔记`（可选，随库惯例）——纯 `[[链接]]` 跳转列表，不写关系注解；与上节分工：上节答「它和谁是什么关系」，本节只答「还有谁值得点过去看」；两者并存时，本节不含已在上节出现的链接
8. `>[!references]`（附录，只放正文放不下的）——**本地实验底账**（完整命令、参数、环境版本；正文只留场景与数字）、**逐字引文底账**（正文转述处的原文摘录）、**离线无链接来源**（纸质书等，注明获取方式）、**待考项清单**（正文内联「待考」的汇总与原因）、**图片来源**（来源图出处 / 自绘图依据）。正文已内嵌链接的来源**不重复罗列**，否则又是双份

> 角色定重心是写作流程的事（见写作技能「阶段一」），但两条契约**对所有角色成立**：**前置概念**——读者是初学者，凡依赖未展开知识即须在开篇交代（结构契约第 3 条）；**深度契约**——机制/原语篇讲清「为何这样设计」，惯用法/应用篇讲清「为何这样选」，综述篇讲清「为何演化成这样」。

## 3. 深度契约（所有角色都成立）

初学者的困难不在「记不住结论」，而在「不知结论从何而来、为何长成这样」。凡有据可查处，正文必须回答三问；无据不写、不编：

| 问 | 要讲什么 | 未讲透的判据 |
| --- | --- | --- |
| **因果** | 机制 / 参数 → 后果 → 后果的后果，显式成链（如「03h 零空周期 → 器件无准备时间 → 被单独降档至 50 MHz」） | 删掉中间环节，读者能否自行补上？不能即未讲透 |
| **设计取舍** | 有别的做法吗？为何选它？代价是什么？代价由哪个具体设计决定造成、谁买单？ | 只说了「它是这样」，没说「为何不是那样」；代价未落到具体设计决定 + 结构级证据（字段表/签名）+ 买单方 |
| **历史成因** | 何时 / 为何引入？留下什么兼容包袱？ | 怪设计被当成「本来就该这样」 |

- **取证**：三问同受 §1 约束——设计动机引官方理由（源码注释、应用笔记、官方 KB、官方员工答复），历史引旧版文档 / 标准修订史 / 勘误（errata）/ 迁移指南；查不到内联「待考」，**不得凭常识替设计师编动机**（推断内联「（推断）」并给理由）
- **落点**：篇幅小则融入相关段（因果链融进机制讲解，历史成因放动机段），成体系则单开一小节；不强制独立标题，禁止为凑结构造空节
- **边界**：只讲与本篇角色相关的「为何」；无关的动机 / 历史 `[[引走]]` 给兄弟条目

## 4. 干货契约

**干货**：可直接影响判断或决策、且读者自己想不到 / 查不到的具体信息。四种形态——**数字**（阈值、上限、量级、比例）、**公式**（把关系写成式子）、**判定规则**（何时选哪个：决策表 / 分支树）、**反直觉结论与生产坑**。

> [!warning] 反判据：堆参数不是干货
> 参数罗列、面面俱到的选项清单、复述手册目录、无决策含义的「完整性」都不是干货。判据：**删掉它，读者做决策会不会错？** 会 → 干货；只是「更完整」→ 手册拷贝，删。

库内达标样本（照此手感写）：
- 因果链 + 设计取舍 + 反直觉结论：[[标准 SPI 的带宽瓶颈 Standard SPI Bandwidth Bottleneck]]（「空周期不是浪费，是买频率的门票」；「133 MHz 是除 03h 外所有命令的上限」）
- 历史成因 + 兼容包袱：[[长文件名与 Unicode Long File Names and Unicode]]（「FAT 诞生时……又不能破坏老系统——于是……」）
- 官方设计取舍逐字：[[SFDP 参数表 SFDP Parameter Table]]（引 `sfdp.c` 注释说明「一次读全部参数头」的取舍）

## 5. 行文契约（操作化定义）

- **深入浅出** = 例子先于机制先于边界
- **不啰嗦** = 无开篇俗话、无复述正文的总结段、每段都载信息
- **朴实** = 平实直陈，修饰最小化：无感叹号、无排比与抒情修辞、无「值得一提 / 众所周知 / 毋庸置疑」类填充语；无「钉死 / 摆齐 / 划清界限 / 自证」类修辞化动词（改直陈：定义 / 并列 / 区分 / 体现）；形容词副词能删则删，让断言与证据自己说话；收束句与转折句直陈因果，不用对仗、回环与杂糅比喻（「这条账把 X 划出了协议边界」）——「账 / 笔」只作段落框架标记（第一笔 / 第二笔），不充当动作主语
- **高密度** = 每句必载新信息：无空洞过渡句、无同义反复；短句直给，一句一个断言或一个因果步
- **流畅** = 段间衔接自然、无逻辑跳步，读者无需回看补上下文；枚举性机制规则（解析、对账、流程步骤）用「先 / 再 / 最后」等序次词分句，不挤成一句分号串
- **因果显式** = 把「因为 → 所以 → 导致」写出来，不把推导留给读者；面向初学者，越是自己觉得「显然」处越要展开。新概念、新参数、公式首现前，先一步写明它回应什么需求（缺它会怎样）——不得凭空掉落；机制的方向性命题写准：「携带」与「依赖对端已有」是相反命题，混说即学错
- **实测叙述平实成场景** = 实测断言写成「做了什么 → 看到什么 → 数字说明什么」的平实场景，并点明实测对象与目的（验证哪条行为断言、给正文哪处论证供证），不写「（实测：数字）」式括弧快照旁注；完整命令、参数、文件名不进正文（references 本地实验条目记录），不添「亲手」「称一帧的重量」类表演性动词与比喻——数字与算式自己说话
- **实测表述环境中性** = 正文不写「本机 / 本地」类个人视角词，环境用版本表述（「GStreamer 1.28.2 实测」）；环境与完整命令底账在 references
- **动用的名字首现即注** = 正文使用的工具、格式、产物名（如 gst-launch-1.0、Ogg、WAV）首现处给一句白话：谁制定、是什么、通常干什么——「可独立阅读」的承诺覆盖它们，不只是前置笔记
- **总起对账** = 总起句声称「A 带来 N 个问题/代价」时，逐个核对分论点前提确能从 A 推出；前提不同源就并列、各表前提，不强行归于一因（虚假归因比无总起更误导）；总起按层/逐项承诺代价（如「每层解法都有代价」）时，逐层/逐项点名承接（其一…其二…其三…），原书未标代价的项明说账在何处、去向哪篇
- **概称词点名** = 「这 N 个问题」「两笔代价」「一件东西」类概称与代词，首现处点名映射对象，后文方可复用
- **开放列举标穷尽性** = 列举的对象域不止笔记所列（规范原文有更多项）时，要么穷尽、要么以「等」收尾并在依据处声明全表出处；不以无标记的子集冒充完备清单——读者会把未列项当成「不成立/不兼容」
- **叙述体成文，不用答句腔** = 段落按文章自身叙事展开：从上文自然引出对象再下定义，关键新概念给成句定义而非括注带过（如「元素类别——每个元素注册时附带的层级分类字符串」）；禁止「先明确 X」「所谓 Y 是指」类回答姿态开段——正文是文章不是答问，所谈问题的上下文由正文自己给出
- **关系写方向** = 讲两个机制的关系显式写谁建立在谁上、交叉点往哪走（如「属性变化的通知借信号发出」），不用「相关/配合」含糊带过
- **对应断言逐对点明** = 称「A 与 B 对应」时逐对给出映射——对照表逐行「A｜B｜各自角色」，或句中成对点名；两串各自裸列（如类别一串、元素一串）不算讲了对应
- **反例/失败模式自洽** = 正文给出的「反例/失败模式/选错后果」示例凡涉及沿、时序、状态位，须以本篇已给的定义与表格为唯一基准逐沿核对，示例中的沿方向不得与正文定义矛盾（强度对齐 §6「图文一致、正文修订后回查」）
- **成段展开** = 初学者读的是讲解不是私人速记：每个要点写成完整句段（主张 → 现实/机制 → 由此产生的后果与应对），条目清单只作骨架不作最终形态
- **歧义词先拆维度** = 术语混含多个独立概念时（如「集中」＝逻辑/物理/管理三件事），先显式列出各维度，再让例子逐维度对号入座；不指望读者从「集中式」自行联想到「逻辑上集中」
- **中文术语准确** = 取该领域标准译名；无标准译名用通行译名并保留英文；不直译、不造词（如 stub 译「存根 / 桩」，不意译「替身」）
- 中文正文；术语首现中英并列，机制性术语与成对的对立术语（canonical / deterministic）各给一句成句定义——它是什么、它要求什么；中英并列不等于定义，论断落到定义上；缩写首现旁标全称（`速率单调调度（Rate-Monotonic Scheduling, RM）`），后文方可只用缩写；标识符用行内代码；数学用 $…$
- **待考/推断内联轻量**：「待考」「（推断）」内联在句子流中、不加粗、不打断阅读；推断给理由（如「推断自执行位置模型」）。取证状态不是正文主角，链接与断言才是
- **破折号留空格** = 破折号「——」前后各留一个半角空格；表格内独立占位表示「无」的 `——` 不在此列
- **不借他人评语立论** = 原书/原作者的评价与姿态（「X 的评语是…」「X 点破」「X 犀利地指出」「X 写得明白」「官方那句 X」「官方同样指出」「写得更直接」「列举不留余地」「单设专页作答」）不上正文；判断化为自己正文的直接陈述，出处只留链接/页锚。中性事实归因可（「官方为此单设了专页」「官方把改动分成三档」）——禁的是评价来源的措辞与姿态
- **概念首现给 wikilink** = 正文解释性依托的概念（如「套接字之上的第一层抽象」中的套接字），库内有条目的在首现处给 `[[条目|显示名]]`，显示文本保持行文自然（不必用全名）
- **同句不重复点名** = 刚以 wikilink 或全称点名的概念/篇章，同句内再次提及时用「该篇 / 它」指代；「已指出 / 已落地」类完成体助词非必需则省
- **先定义后使用** = 专有名词（组织、规范、产品）首次被引用其陈述前，须已在先文给出全称与一句定位（如先在历史沿革引出「分布式计算环境（DCE）」，再引其目标陈述）；不用「官方设计」类无所指修饰语充当出处主语

## 6. 图片契约（需要才用，宁缺毋滥）

- **何时用**：结构关系、分类树、流程/状态机、时序等纯文字表述吃力处；一篇 0–5 张，不为配图而配图。能无损映成一张对照表的分类（类 × 条目两层的分类树）用表不用图——表格零渲染依赖，也免去渲染核对；删图时同步清除 references 里的图底账条目，不留孤儿。图是表达工具，不是断言依据（官方文档原图除外）
- **来源优先级**：官方文档/数据手册原图 > 经典教材插图 > 社区图解；不用营销图、水印图、与正文所述版本不符的旧版图；无合格现成图、或现成图与正文角度/版本不符时，**自绘**（见下条）
- **两条获取途径**：
  - **下载**：现成图经 webfetch / `curl -L` 下载
  - **自绘**：手段按图选形——结构图、分类树、分支树手写 SVG；流程、状态机、时序用 PlantUML 代码块（vault 惯例；首行 `skinparam defaultFontName "Noto Sans Mono CJK SC"` 定中文字体，PlantUML 插件输出 SVG 天然清晰，不用 dpi/zoom 调尺寸），Mermaid 备选；直接写在正文，不产生图片文件；数据图、函数图用脚本生成（graphviz、matplotlib 等）；布局复杂或拿不准的图可丢给多模态模型（经 task 委派视觉向子代理，如 visual-engineering），只交代内容要点、格式与术语要求。无论亲自写还是委派，图中内容只能图解正文**已核实**的断言，不得借图引入新断言
- **存放**（文件类图统一）：vault 根目录 `pictures/`；文件名用描述性中文（如 `函数调用形式.png`），不用 `Pasted image …` 时间戳名；保留原格式（png/jpg/svg/webp 均可）
- **必须实际渲染核对（下载图与自绘图一律，委派产物同）**：下载图下载后打开、自绘图定稿后渲染打开、Mermaid 预览渲染——确认内容支撑正文断言、图中标注与正文术语一致、无文字重叠或截断；图文不符宁可不用；无本地渲染环境时，改用 Obsidian 内建渲染的 Mermaid 或经有渲染环境的一步补核——未经渲染核对的自绘图不得定稿，核对记录（命令、日期、目检结论）写入 references 自绘条
- **图文断言对照，修订后回查**：图的每条边、每个标注能指认对应正文哪条断言；正文修订后回查图并同步（正文把直连改出两跳寻址，图的压缩边要跟着拆）——初学者应能仅凭图重建正文机制路径，缺步即改图；图内出现的机制术语若正文尚未定义，改图加括注或在图后紧邻句补白话——不让读者带着未定义词读图（图常先于正文解释出现）
- **引用**：文件图用 `![[文件名.png]]`，需要控宽时 `![[文件名.png|400]]`；Mermaid 直接是正文代码块。来源图在 references 按级列出（链接 + 出处章节，注明「图解了哪条断言」）；自绘图在 references 注明「自绘（依据正文哪条断言）」，不占来源分级
