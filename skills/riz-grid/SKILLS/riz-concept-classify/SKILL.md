# Concept-Classify — 教科书式线性归类

把一个概念（concept）安放到本笔记库（`反刍/` Obsidian vault）已有的知识结构中，遵循**教科书式、线性化**的组织原则：先判学科，再定主题，最后定它在学习序列里的精确位置，并按既有命名/格式惯例落地笔记与交叉引用。

> 本 skill 的所有"惯例"都来自对 `反刍/` 现有结构的实证观察（见下文「Vault 惯例速查」）。**不要发明新约定**；遇到现有结构无法容纳的概念时，先向用户提议新增分类，获许后再动手。

---

## 0. 前置检查

1. 当前工作目录或上层存在 `反刍/` vault。若不存在，停止并告知用户路径。
2. 用户已给出**待归类的概念**（至少一个名字）。若只给了领域没给概念，或反之，先补问一句再继续。
3. （可选）用户可能附带：概念的解释 / 一段引用 / 一个 PDF / 一个源链接。有则用作笔记内容种子；无则由你先起草定义占位，标注 `TODO` 待用户补全。

---

## 1. Vault 惯例速查（必须遵守）

这些是从现有结构实证得出的硬约定。**违反任何一条都会破坏线性一致性。**

### 1.1 目录层级

```
反刍/
├─ <学科> [<英文>]            # 顶层学科，中英并列，如 "Operating System 操作系统"
│  ├─ <主题>/                 # 主题目录，如 "基本概念"、"对象模型"、"STL/容器"
│  │  ├─ 0. 大纲.md           # 主题大纲
│  │  ├─ xxx.md               # 序列化笔记：章节顺序记录在大纲中
│  │  ├─ xxx.md
│  ├─ <横切概念>.md            # 跨多个主题的概念 → 学科级单文件，如 "类型系统.md"
│  ├─ <主题>/
│  │  ├─ 0. 大纲.md            # 主题大纲
│  │  ├─ 子主题>/              # 子主题目录
└─ ...
```

### 1.2 大纲结构（线性化的核心）

大纲应描述一个主题内的**章节序列**，强阅读顺序，让概念构成递进链条（后者依赖前者）。

**章节的排序依据（决定把新概念插在第几位）：**
基础/原语概念 → 机制/构造 → 惯用法/技术 → 综述/权衡。
即：**先定义、再构造、再用法、后评价**。新概念的排序位置 = 它在学习路径上的位置，不是字母序、不是时间序。

>[!note]
>- `0. 大纲.md` 文件名中的 `0` 仅用于目录排序，让大纲始终排在该主题最前面。

### 1.3 笔记内部格式

- 一级标题用 `# {标题}`，与文件名呼应。
- 代码块带语言标注（` ```cpp `）。
- 引用块用 Obsidian callout：`>[!references]` 或 `>[!参考]`，内部用 `[[wiki-link]]` 指向 PDF/源。
- 中文为主，专有名词也以中文为主，但保留英文原文作为补充（如 `回写模式 Write-back`）。
- 概念对照表用 markdown 表格（见 `基本概念.md`）。

### 1.4 交叉引用

- 用 `[[文件名]]`（不带扩展名、不带路径，Obsidian 会解析）。
- 相关概念之间**双向**接线：在新笔记里引用相关旧笔记，并在合适的旧笔记里补一条指向新笔记的链接。

## 2. 工作流（五阶段，严格顺序）

### 阶段 A · 测绘（Survey）

**目标**：在动手前看清现有结构，避免重复造轮子或放错学科。

1. 列出 `反刍/` 下所有顶层学科目录与各学科的主题子目录（一次 `glob` 或 `ls` 即可）。
2. 在**全库范围**搜索待归类概念的名字（中英文、常见缩写），判断：
   - 是否已存在同义笔记 → 命中则转入「去重/合并」分支（见 §3）。
   - 是否存在 `[[wiki-link]]` 指向一个**尚未创建**的笔记（悬空链接）→ 命中说明用户早有归位意图，优先填那个位置。
3. 锁定 **1 个候选学科** + **1–2 个候选主题目录**。判定依据：
   - 概念的核心归属学科（`epoll` → 系统编程/网络编程；`monad` → 函数式编程）。
   - 该学科是否已有容纳它的**合适**主题子目录：
       - 主题子目录应聚焦同一学习路径或同一机制，避免混合不同抽象层级
       - 若没有合适的子目录，则进入 §4 的新增分类流程

> ⚠️ 这一阶段**只读不写**。不要在测绘期间创建任何文件。

### 阶段 B · 分类（Classify）

**目标**：在候选学科/主题内，把概念的**抽象层级**按严谨依据定下来，据此确认概念在大纲中的排序。

按以下四层之一归类（从下到上是学习顺序的从先到后）：

| 层级  | 问自己              | 示例（C++ 内）                   |
| --- | ---------------- | --------------------------- |
| 原语  | 它是构成其他概念的基础吗？    | `对象 Object`、`类型 Type`、`表达式` |
| 机制  | 它是语言/系统提供的某种构造吗？ | `对象创建`、`数据布局`、`构造函数规则`      |
| 惯用法 | 它是基于机制总结出的使用模式吗？ | `状态转移及资源管理`、`Tag Type 命名`   |
| 综述  | 它是对上述的横向梳理/权衡吗？  | `类型系统`、`0. 大纲`              |

- 原语/机制层 → 通常落在学科的 `基本概念/` 或对应主题目录。
- 惯用法层 → 落在 `惯用法 Idioms/` 或对应主题。
- 综述层 → 学科级单文件（如 `类型系统.md`）或 `0. 大纲` 下。

### 阶段 C · 线性化（Linearize）

**目标**：确定新笔记在大纲中的**精确排列位置**。

1. 查阅目标目录下所有现有笔记及大纲结构，按已确认的排列位置还原它们的隐含顺序。
2. 问：**"学懂新概念，需要先懂目录里哪几个？新概念又是哪几个的前置？"**
   - 找到"新概念必须排在它之后"的最后一个笔记 → 下界。
   - 找到"必须排在新概念之后"的第一个笔记 → 上界。
3. 新概念插入位置 = 下界与上界之间。**若需要，在大纲中重新调整条目顺序**。
   - 若调整大纲会牵动大量既有链接，先 `grep` 检查相关 `[[wiki-link]]`，避免断链。
   - 若调整成本过大（>5 处链接需同步），退而用次优位置 + 在笔记开头写一句"前置阅读：[[...]]"来保序。
4. 若目录尚无序列大纲，且新概念与它们构成清晰链条，借此机会**给整个子目录引入序列大纲**，但须征得用户同意（这是结构性变更）。
5. 大纲可以有层次结构：一个笔记下也可以有子主题

### 阶段 D · 落地（Place）

**目标**：按惯例创建笔记文件。

1. 在主题的**大纲**文件中把笔记文件记录到正确的位置上。
2. 文件名 = 概念名（中英并列，如 `协程 Coroutines.md`）。
3. 笔记骨架（按需裁剪，**不要无脑填全**——没有的内容留 `TODO`，不要编造）：

   ````markdown
   # {概念中文} {概念英文}

   {一句话定义。引用权威来源原文最佳。}

   ## 动机 / 问题背景
   {这个概念解决什么问题？为什么需要它？}

   ## 定义与机制
   {形式化定义 / 代码示例}
   
   > [!quote] [定义的信息源](xxx 链接)
   > {信息源原文，勿翻译}

   ```{lang}
   {代码}
   ```

   ## 与相关概念的关系
   - 上位概念：[[...]]
   - 同层并列：[[...]]
   - 对立/互补：[[...]]

   >[!references]
   >- [[相关 PDF 或源]]
   ````
   其中 `[!quote]` callout 仅在引用权威来源时使用。

4. 横切概念（综述层）不用上面的骨架，改用**对照表**（见 `基本概念.md`）或**分层小节**。
5. 遣词用字和句子需要**精确、简易和严谨**。

### 阶段 E · 接线（Wire）

**目标**：让新笔记被知识网络"看见"，而不是孤岛。

1. 在 §C 找到的**前置笔记**里补一行"后续：[[新笔记]]"或在正文自然处插入链接。
2. 在**同层并列笔记**里互相加 `[[wiki-link]]`。
3. 若新概念**横跨多个学科**（如 `Coroutine` 同时属于 C++ 异步编程与函数式编程），在主学科落地笔记，在副学科创建**轻量指针笔记**（只含一句定义 + `[[主笔记]]`），避免内容重复导致漂移。

---

## 3. 去重 / 合并分支

测绘阶段若发现疑似同义笔记：

1. 对比两侧的定义、抽象层级、引用来源。
2. 三种处理：
   - **完全同义** → 合并到更规范的那一篇，另一篇改为指针（或删除并清理断链）。
   - **同根但层级不同**（如"对象"原语 vs "对象模型"综述）→ 各自保留，互相用 `[[wiki-link]]` 显式区分。
   - **不确定** → 列出差异请用户裁决，不要擅自删除。

---

## 4. 新增分类分支

若现有学科/主题都无法容纳（例如一个全新子领域）：

1. **先提议，后动手**：向用户说明"建议在 `<学科>` 下新增主题目录 `<名字>`，理由是 …"。
2. 获许后：创建目录 → 创建大纲文件 → 放入首篇笔记 → 在学科级综述（若有）登记新主题。
3. 新目录命名沿用中英并列惯例（如 `Meta-programming 元编程`）。

---

## 5. 完成校验（交付前必做）

- [ ] 新笔记在序列大纲中反映其学习顺序
- [ ] 新笔记文件名符合**本技能**的惯例
- [ ] 新笔记内部格式符合 §1.3。
- [ ] 所有受大纲调整影响的 `[[wiki-link]]` 已更新（`grep` 验证无断链）。
- [ ] 至少与 1 篇现有笔记建立了双向交叉引用（不是孤岛）。
- [ ] 未引入任何本 skill 未授权的新约定（新前缀样式、新目录层级等）。
- [ ] 向用户报告：落在哪条路径、为什么是那个序号、改动了哪些旧文件。

---

## 6. 反模式（不要这样做）

- ❌ 按字母序或时间序编号——序列必须是**学习顺序**。
- ❌ 把概念塞进"看起来沾边"但抽象层级不符的目录（如把惯用法放进 `基本概念/`）。
- ❌ 创建没有交叉引用的孤岛笔记。
- ❌ 在多个学科**重复落地**同等内容——用指针笔记代替。
- ❌ 未经用户同意就重构整个目录的编号方案。
- ❌ 编造定义/来源；无依据的内容留 `TODO`。
